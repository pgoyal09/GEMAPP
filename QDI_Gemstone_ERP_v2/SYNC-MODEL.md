# GEMAPP Sync Model

Formal specification of the Supabase cloud sync model for QDI Gemstone ERP v2. This is a documentation-only artifact — no sync logic changes are implied.

**Owner files:** `Services/Supabase/` (SupabaseSyncService, SyncDTO, SyncTracker, SupabaseAuthService, SupabaseManager)

---

## 1. Design Intent

### Offline-first, local source of truth

The app is a native macOS desktop ERP. SwiftData is the authoritative data store. Supabase is a replication target for backup, cross-device visibility, and future multi-device scenarios. The app must be fully functional with no network connection.

### Sync is optional

If Supabase credentials are missing from `Info.plist` / `UserDefaults`, `SupabaseManager` marks sync unavailable and the app operates in local-only mode. The UI degrades gracefully — sync controls are hidden or disabled.

### Single-user assumption

The current sync model assumes one active user per Supabase account. `user_id` is stored on remote rows but is not used for row-level security or tenant isolation. Multi-device concurrent editing is not supported and will produce silent overwrites.

---

## 2. Sync Operation Flow

### Entry points

| Method | Behavior |
|---|---|
| `syncAll()` | Full push-then-pull cycle (current canonical path) |
| `sync()` | Push-only (legacy, retained for backward compat) |

### Guards

Before any sync operation:
1. `isSyncing == false` (prevents concurrent syncs)
2. Supabase client is available (credentials configured)
3. User is authenticated

### Push-then-pull order

```
PUSH (local → remote)
  1. Customers
  2. Gemstones        (batched, 100/request)
  3. Memos
  4. Invoices
  5. LineItems         (batched, 100/request)
  6. LotTransactions
  7. Payments
  8. HistoryEvents     (batched, 100/request)
  9. RFIDTags

PULL (remote → local)
  1. Customers         (WHERE updated_at > lastSync)
  2. Gemstones         (WHERE updated_at > lastSync)
  3. Memos             (WHERE updated_at > lastSync)
  4. Invoices          (WHERE updated_at > lastSync)
  5. modelContext.save()

POST-SYNC
  - lastSyncDate = now
  - pendingChanges = 0
```

**Push always uploads all local records** (no delta tracking). Each entity type is upserted to the remote table with `onConflict: "id"`.

**Pull is filtered** by `updated_at > lastSync` per table, so only rows changed since the previous sync are downloaded.

### Batching

Gemstones, LineItems, and HistoryEvents are chunked into 100-record batches to stay within Supabase payload limits. Other entities are sent in a single request per table.

## 4. Identity Model

Each entity uses a **deterministic UUID** for its remote `id` column, generated by `stableSyncID(entity:hashValue:)`. This function derives a UUID v5-style identifier from the entity type name and the SwiftData `persistentModelID.hashValue`. The same local record always maps to the same remote UUID, making push upserts idempotent.

During pull, entities are matched by **business key** (not by remote UUID), because local SwiftData records use auto-generated `PersistentIdentifier`, not the sync UUID.

### Identity rules per entity

| Entity | Remote ID | Push Upsert Key | Pull Match Key | Business Key Field |
|---|---|---|---|---|
| **Customer** | `stableSyncID("Customer", ...)` | `id` | `email` | `email` (unique) |
| **Gemstone** | `stableSyncID("Gemstone", ...)` | `id` | `sku` | `sku` (unique, format: `TYPE-SHAPE-GROUP-NNN`) |
| **Memo** | `stableSyncID("Memo", ...)` | `id` | `referenceNumber` | `referenceNumber` (unique) |
| **Invoice** | `stableSyncID("Invoice", ...)` | `id` | `referenceNumber` | `referenceNumber` (unique) |
| **LineItem** | `stableSyncID("LineItem", ...)` | `id` | *(no pull)* | — |
| **LotTransaction** | `stableSyncID("LotTransaction", ...)` | `id` | *(no pull)* | — |
| **Payment** | `stableSyncID("Payment", ...)` | `id` | *(no pull)* | `referenceNumber` |
| **HistoryEvent** | `stableSyncID("HistoryEvent", ...)` | `id` | *(no pull)* | — |
| **RFIDTag** | `stableSyncID("RFIDTag", ...)` | `id` | *(no pull)* | `epcCurrent` |

### Identity assumptions

- Customer `email` is unique across the business — there is no compound key.
- Gemstone `sku` is unique and immutable after creation (generated by `SKUGenerator`).
- Memo and Invoice `referenceNumber` values are unique within their respective types.
- `stableSyncID` is deterministic but based on `hashValue`, which is not guaranteed stable across SwiftData schema migrations or store re-creation.

## 5. Conflict Model

### Strategy: last-write-wins (LWW)

The sync model uses implicit last-write-wins based on the remote `updated_at` timestamp.

**On push:** Every DTO sets `updatedAt = Date()` at conversion time. The Supabase upsert (`onConflict: "id"`) overwrites the entire remote row. There is no conditional check — the local version always wins on push.

**On pull:** Rows are fetched where `updated_at > lastSync`. For each pulled row:
1. Look up local entity by business key (email / sku / referenceNumber)
2. If found: **overwrite all local fields** with remote values
3. If not found: **insert new entity**

There is no field-level merge. The entire entity is overwritten wholesale.

### What this means in practice

| Scenario | Outcome |
|---|---|
| Local edit, then sync | Local pushes to remote, overwriting remote row |
| Remote changed, then pull | Remote overwrites local fields for that entity |
| Both changed between syncs | Push runs first → local wins on remote. Pull runs second → remote (which now has local data) comes back. Effectively: **local wins** in a single sync cycle. |
| Two devices edit same entity | The device that syncs last overwrites the other's changes. No merge, no conflict detection. |

### Non-mergeable fields

All fields are overwritten on both push and pull. There is no selective merge for any entity.

### Relationship handling during sync

**Push:** Foreign key references (`customerId`, `gemstoneId`, `memoId`, `invoiceId`) are stored as optional UUIDs in DTOs. Relationships present on the local model are converted to the related entity's `stableSyncID`.

**Pull:** Relationship fields are set to `nil` during pull conversion. The pull logic does not re-link relationships to local SwiftData objects. This means pulled entities may have orphaned or missing relationship references until the next local edit re-establishes them.

## 7. DTO Field Mapping

All DTOs use `CodingKeys` for `camelCase ↔ snake_case` conversion. Notable transformations:

| Local Type | DTO Type | Notes |
|---|---|---|
| `Decimal` | `Double` | Precision loss possible for cost/price fields |
| Enum (e.g., `StoneType`) | `String` (`.rawValue`) | Human-readable in remote DB |
| Relationship | `UUID?` (`stableSyncID` of related entity) | `nil` on pull; populated on push |
| `Date` (createdAt) | `Date` | Preserved from model |
| `Date` (updatedAt) | `Date` | **Always set to `Date()` at conversion time** |

### Timestamp behavior

`updatedAt` is always set to the current time when a DTO is created for push, regardless of when the entity was actually last modified. This means every pushed record appears "just changed" on the remote side. This is intentional — it ensures the push always wins — but it defeats any remote-side `updated_at` ordering for audit purposes.

## 8. Known Risks and Assumptions

### R1: Push-only entities cannot be restored from remote

LineItems, LotTransactions, Payments, HistoryEvents, and RFIDTags have no pull implementation. If the local store is lost, these entities cannot be recovered from Supabase. They exist on the remote only as a secondary copy.

### R2: Relationship orphaning after pull

Pull sets all relationship fields to `nil`. A pulled Gemstone will not be linked to its Customer; a pulled Memo will not be linked to its LineItems. Relationships are only correct when they originate from local creation/edit.

### R3: No conflict detection or logging

When a pull overwrites a local entity, there is no log entry, no user notification, and no ability to review or revert the change. Silent overwrites are the only conflict resolution path.

### R4: `stableSyncID` depends on `hashValue` stability

The deterministic UUID is derived from `persistentModelID.hashValue`. If SwiftData changes hash behavior across OS versions or schema migrations, the same entity could produce different remote UUIDs, creating duplicates on the remote side.

### R5: Decimal → Double precision loss

Cost, price, and rate fields are stored as `Decimal` locally but converted to `Double` in DTOs. For high-precision financial values, this can introduce rounding differences between local and remote.

### R6: No incremental push

Every sync uploads all local records for every entity type. For large inventories, this is bandwidth-intensive and creates unnecessary remote writes. There is no dirty-flag or change-tracking mechanism.

### R7: No soft delete propagation

Hard deletes on the local side are not propagated to Supabase. Deleted local records remain as orphaned rows on the remote. There is no tombstone or delete-sync mechanism.

### R8: Clock skew sensitivity

Both push (`updatedAt = Date()`) and pull (`WHERE updated_at > lastSync`) depend on clock accuracy. If the local clock drifts, pull filters may miss or duplicate rows.

### R9: No retry or partial failure recovery

If sync fails mid-operation (e.g., after pushing Customers but before pushing Gemstones), there is no rollback or resume. The next sync will re-push everything, which is safe due to upsert idempotency, but pull timestamps may be stale for tables that didn't complete.

## 9. Future Guardrail Opportunities (not yet implemented)

These are documented for planning purposes. No code changes are implied.

1. **Identity assertions** — runtime checks that business keys (email, SKU, referenceNumber) are non-empty before sync
2. **Duplicate detection** — pre-push check for remote rows with same business key but different `id`
3. **Sync audit log** — structured log of each push/pull with entity counts, conflicts detected, and errors
4. **Relationship re-linking on pull** — resolve foreign key UUIDs back to local SwiftData objects
5. **Pull coverage for all 9 entities** — extend pull to LineItems, Payments, LotTransactions, HistoryEvents, RFIDTags
6. **Incremental push** — dirty-flag tracking to avoid re-uploading unchanged records
7. **Soft delete propagation** — tombstone mechanism for remote cleanup
